## Integration Paths

- Hosted or embedded checkout through Paymob's documented API path.
- Payment methods vary by merchant/account and region: cards, wallets, kiosk, installments, Apple Pay, and BNPL where enabled.
- Plugins/no-code are supported separately; still require server-side order reconciliation for custom fulfillment.

## Setup Prerequisites

- Merchant account, API credentials, integration IDs, HMAC secret, payment method enablement, callback URLs, and sandbox/live separation.
- Confirm region and dashboard generation because older/newer Paymob dashboard terminology differs.

## Auth And Secret Boundary

- Keep API keys, HMAC secrets, integration secrets, and server-side payment creation credentials in backend env only.
- Frontend may receive only public checkout tokens/URLs or client-safe identifiers generated by the server.

## Callback Or Webhook Contract

- Treat Paymob processed callbacks as the source of truth for fulfillment.
- Response/redirect callbacks are useful for UX, but the page should remain `processing` until a verified server-side callback or documented inquiry confirms final payment state.
- Store Paymob transaction id, order id, integration id, amount, currency, pending/success flags, and callback receipt timestamp.

## Signature Or HMAC

- Transaction callback HMAC uses SHA-512 with the merchant HMAC secret over Paymob's documented ordered values.
- The transaction HMAC field order from the public docs/user-provided excerpt is: `amount_cents`, `created_at`, `currency`, `error_occured`, `has_parent_transaction`, transaction id (`obj.id` for processed POST or `id` for response GET), `integration_id`, `is_3d_secure`, `is_auth`, `is_capture`, `is_refunded`, `is_standalone_payment`, `is_voided`, order id (`order.id` for processed POST or `order_id` for response GET), `owner`, `pending`, `source_data.pan`, `source_data.sub_type`, `source_data.type`, `success`.
- Compare calculated HMAC with the received `hmac` query parameter using constant-time comparison.
- Card-token HMAC has its own documented field checklist; do not reuse transaction HMAC ordering.

## Idempotency Keys

- Unique local order reference plus Paymob order id and transaction id.
- Process duplicate callbacks as no-ops after the first valid final transition.

## Amount And Currency

- Paymob uses `amount_cents` for many API/callback flows; compare to local smallest-unit amount exactly.
- Compare currency and local order reference before marking paid.

## Status Mapping

- `success=true` and `pending=false` after valid HMAC can map to paid/confirmed.
- `pending=true` remains pending.
- Error, failed, refunded, voided, or capture flags must map to explicit local states without overwriting a stronger final state incorrectly.

## Refunds Voids And Subscriptions

- Refund, void, and capture are documented as managing-payment operations; use only from backend.
- Auth/capture flows require separate state transitions from direct sale flows.
- Subscriptions and saved cards exist in Paymob docs; treat card tokens and recurring permissions as high-risk and never store raw card data.

## Sandbox And Test Notes

- Use dashboard/sandbox credentials and configured callback URLs.
- Automated link checks may report JS challenge for public `.md` docs; manually verify in browser before declaring docs unavailable.

## Unknowns And Do Not Invent

- Do not invent integration IDs, HMAC secrets, endpoint versions, token fields, status names, or enabled payment methods.
- If a merchant account uses older Paymob APIs or dashboard naming, ask for the current merchant docs/screenshots and summarize safely.

## Agent Checklist

- Create payment server-side.
- Store Paymob ids before redirecting.
- Verify callback HMAC.
- Compare amount, currency, transaction id, and order id.
- Fulfill only from verified backend state.
- Make callbacks and redirects idempotent.

## Fail If

- You mark paid from redirect success alone.
- HMAC ordering is guessed.
- Paymob secrets appear in frontend code.
- Amount cents or currency are not compared.
- Duplicate callback creates duplicate fulfillment.
